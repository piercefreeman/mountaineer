# Philosophy & Tradeoffs

Mountaineer connects a Python backend to a React frontend. It generates the types, links, and action calls between them, with conventions for routing and builds. You choose the database and application services.

## What Mountaineer Optimizes For

- Projects that run locally and deploy in a container
- TypeScript hooks and links generated from Python models and controller signatures
- Business logic in Python, with React handling presentation and client interaction
- Server-side rendering and hydration without a separate Node server or a hand-maintained API for page data

## Compared With Django + React

Django + React lets you assemble the backend and frontend independently. You also maintain the API contract between them, including routes and types. Mountaineer generates that contract in exchange for conventions about how controllers, actions, and views fit together.

| Area | Mountaineer Bias | Tradeoff |
| --- | --- | --- |
| Frontend/backend interface | Generate hooks, links, and action wrappers from controller signatures | You adopt Mountaineer's controller and action conventions instead of hand-rolling every API surface |
| Views | React and TSX with server-side rendering | Mountaineer is not centered on Jinja or DTL-style templates |
| Project structure | Disk-based routing and a dedicated `views` project | The filesystem layout is more opinionated than a fully bespoke Django + React setup |

## Separate Webapps

Suppose your FastAPI service now needs a dashboard or a customer settings page. A separate React app gives you independent development and deployment, but also leaves you responsible for keeping its routes and types in sync with the backend.

Mountaineer keeps those pages in the Python project. You use FastAPI's typed parameters and dependency injection in your controllers, then consume their data through generated React hooks. This fits applications where the backend and frontend evolve together.

## What Is Configurable

Most code you write is still ordinary Python and ordinary React.

### Backend

Controllers are normal Python classes. Dependencies use FastAPI's dependency injection system. Mountaineer's HTTP layer sits on FastAPI, which in turn sits on Starlette. The `AppController` also exposes the underlying FastAPI app, so you can still add routers, middleware, and surrounding application services in the usual way.

### Frontend

The `views` directory is a normal React and TypeScript project. Mountaineer reads your `package.json`, `tsconfig.json`, and PostCSS configuration while Vite provides the same CSS pipeline in development and production.

### Data Layer

Mountaineer does not ship with a required ORM or default database layer in its core runtime. Iceaxe is the default in `create-mountaineer-app` and in many examples, but it is not a hard dependency of the framework itself. If you prefer SQLAlchemy, SQLModel, peewee, asyncpg, or another async-friendly data layer, you can wire that through your own dependencies and project configuration.

In practice, switching away from Iceaxe mostly means replacing the generated project scaffolding and database-specific helpers in your own app, not replacing Mountaineer itself.

## What Is Intentionally Opinionated

These conventions are part of the framework:

- The contract between controllers and the frontend is built around `render`, `@sideeffect`, `@passthrough`, generated `.mountaineer` helpers, and disk-based view discovery
- The frontend build pipeline is part of the framework rather than a generic "bring any bundler" adapter
- Mountaineer assumes React is the primary view layer rather than server templates

Swapping the core bundler or replacing the controller-to-frontend contract requires changes beyond project configuration.

## What Mountaineer Is Not Trying To Be

Mountaineer focuses on connecting controllers to views. Features such as authentication, billing, and database access come from your application or separate libraries and plugins. Choose it for the Python/React integration if you are comfortable making those choices yourself.

## Roadmap

Follow the GitHub [issue tracker](https://github.com/piercefreeman/mountaineer/issues) for planned work and current limitations. If your application depends on a particular feature or extension point, check its status there before choosing the framework.
